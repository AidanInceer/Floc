Floc v1 — physical data model

The schema of record is db/schema.ts. This diagram mirrors it — change both in the same commit, or one of them is lying.

Assume id (PK), created_at, deleted_at and last_modified_at on every entity — omitted below to keep the blocks readable. fx_rate is the one exception, noted where it appears.

user / account / session / verification are Better Auth's own tables, used unmodified. Only the user anchor is drawn here.

fx_rate stands apart: it is a cache of published rates, owned by nobody, so it has no foreign keys and no deleted_at.

A "stop" (e.g. "3 nights in Rome") is not a table — it's derived by grouping consecutive day rows that share the same overnight_place_id.

Reordering therefore writes no order column: there is none, on day or anywhere else. Dragging a stop or a day permutes what the day rows hold — day.overnight_place_id and the day_event rows' day_id — while the dates stay put (src/server/itinerary.ts). Two consequences fall out of the FKs above: expense.day_id points at a date, so money stays on the day it was spent; and note rows are scoped to day_event.id, which doesn't change, so a thread travels with its event for free.

Balances are never stored. A member's position is derived at read time, per currency, as the sum of what they're owed on expense_split rows minus the settlement rows they've since paid or received (src/lib/money.ts, computeBalances). An expense is what a bill implies about who owes who; a settlement is real money that has since moved off-app (cash), recorded as an immutable fact. Reverting either — a mistaken settle-up, a wrong expense — is a soft-delete, and the balance recomputes as if the row never existed. Deleting an expense under a settlement can tip a balance negative: an honest overpayment, not an error. When every currency's balances net to zero the whole trip reads as settled.

note is the discussion thread on anything that has one. In use today for scope: "day" and scope: "day_event" (whatever the group needs to know about that ferry), read scoped by (trip_id, scope, scope_id) off note_scope_idx. One table rather than day_comment + day_event_comment + …: a note is the same object with the same author-or-admin delete rule wherever it hangs.

note.parent_id makes a reply, and threads are exactly one level deep (v0.2 ticket 06): addNote walks up before inserting, so replying to a reply attaches to that reply's own parent and the shape can't drift however the UI changes. Deleting a top-level comment soft-deletes its replies with it — a reply is only legible under the comment it answers. Unbounded nesting was rejected on render grounds: a thread draws in a narrow panel, where a fourth level would be a few words a line.

note.edited_at marks a comment its author has rewritten, and the UI says "edited" beside the timestamp. Editing is deliberately not an admin power (rule 6 — admin powers are exactly three): an admin can delete a comment, which is unambiguous, but never put different words in someone's mouth under their own name. last_modified_at can't stand in for this — it is for debugging only and moves for reasons the author never chose.

note_reaction is the three fixed reactions — heart, thumbs up, thumbs down — independent of each other — a note can carry all three. Un-reacting soft-deletes the row and re-reacting revives it, so note_reaction_one_idx is unique on (note_id, user_id, kind) and deliberately excludes deleted_at — the dead row is the row the upsert wants to land on (ticket 115, migration 0005). It was originally non-unique on the reasoning that reviving needs the row to survive, which is the same fact read backwards: without uniqueness the toggle was a read-modify-write over nothing, and two concurrent taps wrote two rows, after which one person's heart counted as two. friendship_pair_idx has the same shape for the same reason. Every read still filters deleted_at.

trip_link is the link shelf (ticket 103) — the listings, timetables and documents a group keeps coming back to, beside the trip thread in the Days pane. Its own table rather than a note with a URL in it, because the two behave differently: a note is something someone said, ordered by when they said it and answerable with a reply, and a link is a reference that has to stay findable a fortnight later. url is http/https only, normalised by readWebUrl before it is stored — the shelf renders hrefs another member typed, so a non-web scheme must never reach the row.

trip_note_doc is the Notes document (ticket 238) — the free-form page that replaced the Ideas tab. One row per trip, holding the whole document as a single JSON blob of editor blocks, never parsed server-side. Whole-doc rather than a row per block because the editor already owns block order and nesting, so a table of blocks would mean keeping two orderings honest for a read nobody makes. Saves are last-write-wins (rule 7): two people typing at once is a known gap, not a solved one. The idea board that once sat inside it as a custom block is gone, along with the idea and idea_vote tables and every note scoped to one (migration 0023); a stored document still holding the block simply drops it on load.

document is a trip file (ticket 239) — a booking, a ticket, a visa scan. It mirrors packing_line's split rather than inventing a second one: owner_id null means shared with every member, and set means private to that one person and never read for anyone else. The bytes are not in the database — they sit on a storage volume under an opaque generated storage_key, and this row is the only thing that knows which trip they belong to, so every read of them goes through requireTripAccess and the owner-scoped access.document resolver first. The key is generated rather than derived from the file's name: a key the uploader chooses is a key the uploader can aim at another trip's file. Deleting is soft (rule 8) and is the uploader's alone — deliberately stricter than a shared packing line, which any member may drop. category is one of five buckets (travel / stay / tickets / admin / other), defaulted rather than required and changeable from the row afterwards: filing is a habit, not a fact, and an unknown value falls to other rather than refusing the file. A file can also sit in the itinerary (ticket 320): day_id and day_event_id are both nullable and both set null, so a ticket parked on the ferry event survives that event being deleted — it simply comes unattached, never binned.

trip_invite is a named invite (ticket 146) — one person asked one friend onto one trip, answered in-app on the invitee's next load. Deliberately not a trip_membership row with a status column: membership is what every trip read tests, and teaching those queries to say "a member, but only the accepted kind" is how rule 5's enumeration-proofing springs a leak. A pending invite grants nothing at all; accepting it writes the membership, and that write is the only thing that changes what anyone can see. trip_invite_pair_idx is unique on (trip_id, to_user_id) and excludes deleted_at, the same shape as friendship_pair_idx and for the same reason — declining leaves the row behind, so re-inviting has to land on it rather than insert a second. The anonymous share link (trip.invite_token) is unchanged and untracked: whoever holds it joins, and nothing here records that they were sent it.

day deliberately has no notes column. It had one; nobody could say what belonged in it, since the thing a group annotates is an event rather than a whole day. Event details live on day_event.note, the conversation in note.
