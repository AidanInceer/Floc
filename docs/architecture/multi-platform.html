Web, iOS and Android

Floc ships three surfaces from one repo: the web app on Railway, and native apps listed on Google Play and the App Store. Behaviour and functionality are identical on all three. The UI is native to each. This page is the plan; the reasoning, and the roads refused, are in the decision record for #237.

Shape

Logic is shared, screens are not. The web app stays Next.js App Router with Server Components; the phone apps are Expo, with their own screens, talking to the web app over tRPC.

The road not taken. Expo plus react-native-web would render one UI tree everywhere. It is refused: the requirement is native UI per platform, so its only advantage is unwanted. It would also cost a rewrite of 22,548 lines of UI and the loss of server rendering, because react-native-web cannot run a Server Component.

Where things live

  • floc/apps/web — unchanged. The only place with database credentials.
  • floc/apps/mobile — the Expo app, iOS and Android from one codebase. Matched by the existing floc/apps/* workspace glob.
  • floc/packages/floc-core — shared logic, types and tokens. Needs a new floc/packages/* glob in both pnpm-workspace.yaml and the duplicate pnpm field in the root package.json; the two readers disagree across pnpm 9 and 10, so neither copy may move alone.

shared/packages/ is for code crossing ventures. Floc-only code does not belong there.

Reuse boundary

Measured, not estimated: the web app is 40,272 lines, of which lib/ is 6,858. Genuine reuse is about 17%. The apps are worth building for store presence, not for that number.

Data

  • One database, server-side only. The phone never holds Turso credentials.
  • Drizzle schema and migrations stay in apps/web/src/db. schema.ts remains the schema of record.
  • Row types are re-exported from floc-core without the db client.
  • A depcruise rule forbids importing db/ from anywhere but apps/web, alongside the existing rule keeping app/ off @/db.
  • The phone reads and writes only through tRPC, which calls the same server/ modules the web app calls. Soft-delete filtering, requireTripAccess and assertAdmin are therefore enforced once, for both surfaces.

Why tRPC and not REST

The requirement is behaviour that cannot drift. With tRPC, changing a server signature fails the mobile typecheck. With hand-written REST it does not — it fails at runtime, on a phone, days after review. A separate API app was refused: a second deployable, no gain today.

Auth

One Better Auth instance, one user table, two credential styles.

  • Web — cookie session. Unchanged.
  • Phone — bearer token via the expo and bearer plugins, held in the device keychain, never in plain storage.
  • Refresh — the token refreshes on use, matching the long rolling sessions the web already has. No re-authentication in v1 on any surface.
  • Logout is per device. It clears that device credential only; signing out on a phone does not end the web session.
  • Google sign-in uses the native flow on a phone, not the web redirect. Wiring, not architecture.
  • Missing provider credentials still degrade rather than throw — the button is not drawn, on any surface.

Offline

Not built yet, but the data layer is chosen so it can be. The client cache persists to disk when #226 turns it on, which makes offline reads a switch rather than a rewrite.

Offline writes are not promised. Last-write-wins with no optimistic locking (non-negotiable 7) means a queued write replayed an hour later would silently overwrite someone. That belongs to #169, and must be settled before offline writes are attempted.

Delivery

Deploying on push to main cannot mean the same thing for a store as for a server.

  • Web → Railway on push to main. Unchanged.
  • Phone, JavaScript-only change → EAS Update. Minutes, no review.
  • Phone, native change → full EAS build and store review. Days.

The rule for which is which. A change is native — and needs a build — if it adds or upgrades a package containing native code, changes a permission, entitlement or bundle identifier, changes the icon, splash or app name, or bumps the Expo SDK. Everything else is JavaScript-only and ships by update. An update may not change what the app is for; a change of purpose needs a build and a new review whatever the diff looks like.

Versions. The commit convention bumps floc/apps/web/package.json. A store build cannot use that. floc/apps/mobile carries its own version, bumped only when a build is submitted, with the build number incremented per submission.

CI. pnpm verify gains typecheck, lint and test for floc-core and floc/apps/mobile. The matching .github/workflows/ check job changes in the same commit, as ever. Store builds are not part of verify — they are triggered deliberately, not on every push.

Payments

Apple and Google both require that anything unlocking features inside the app is sold through their billing rather than Stripe, at 15% for a small business and 30% above it. Stripe is unaffected on the web.

  • First release: the app shows Pro features but sells nothing. Upgrades happen on the website. No commission is paid, and the app does not steer the user to the web to pay — which store rules forbid.
  • Later: native in-app purchase beside Stripe, with one entitlement truth in server/entitlements regardless of which processor took the money. Deferred, not refused.

Budget

Apple Developer Program $99 a year. Google Play Console $25 once. EAS has a free tier with queued builds and paid tiers above it. No Mac is needed — EAS builds iOS in the cloud and submits from there.

Slices

Ordered. Each ships alone. The first two are worth doing whether or not a phone app is ever built.

  1. floc-core carve-out — pure logic and row types out of apps/web, plus the depcruise rule blocking db/ imports from outside it.
  2. tRPC router over the existing server/ modules. The web app is untouched.
  3. Design tokens package, so the two UIs cannot drift on look.
  4. Expo app skeleton — boots, signs in, lists trips over tRPC. The first point at which a phone app exists.
  5. EAS pipeline — build profiles, update channel, CI job, verify.sh, the mobile versioning rule.
  6. Mobile screens to MVP parity — trips, itinerary, expenses, roster. Several tickets.
  7. Store readiness — icons, splash, listings, privacy labels, developer accounts.
